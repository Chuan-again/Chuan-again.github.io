本文记录 sa8797 平台上 Audio FW 与 Audio HAL 进行进程间通信的 AIDL 接口，并讲解其中比较重要的几个接口。

一、背景：从 HIDL 到 AIDL + FMQ

sa8797 项目使用的是 Android 16，与 Android 14 以前不一样：FW 与 HAL 交互使用的是 AIDL + FMQ，去掉了 HIDL。但本质上 HIDL/AIDL 底层都是使用 Binder 进行通信。

Binder 通信的几个基础点：

  • 内核 Binder 驱动通过 mmap 映射了 128KB 的接收缓冲区，数据直接拷贝到目标进程的 mmap 区域，无需中间再拷贝到内核、再拷贝出来。
  • Binder 驱动维护线程池，默认 16 个线程，请求并发处理，因此 Server 端方法需保证线程安全。
  • HIDL 中常提到的 passthrough 模式：HAL 实现库是以直接 dlopen 方式加载（in-process）；而 binderized 模式：HAL 是独立进程，通过 Binder 通信。

二、核心接口：IModule.aidl

文件路径：

这个 AIDL 是 FW 与 HAL 交互的重要接口定义，替代了 HIDL 的 IDevicesFactory + IDevice：

parcelable 可以理解成一个结构体定义。其中的 IStreamOut、StreamDescriptor 都是利用 AIDL 定义的 parcelable，StreamDescriptor.aidl 就是定义该结构体的文件，感兴趣可以去里面看一下具体有哪些结构的定义。

openOutputStream 返回打开的 stream 流时，会创建 FMQ 的描述：上层通过 OpenOutputStreamReturn 的返回值拿到底层 HAL 创建的 FMQ 描述符，进而与 Audio HAL 进行通信。

为什么 Android 要定义 AIDL 文件来当结构体定义，而不直接通过 .h 文件定义？

因为 StreamDescriptor 定义的内容会被 HAL 层、FW、甚至 App 侧引用；使用 AIDL 生成的头文件，就不需要维护三套定义。

2.1 openOutputStream 的入参

AParcel_readData 遇到 IStreamCallback 这种 binder 字段时，会把 parcel 里的强 binder 就地构建成 BpStreamCallback 代理（服务端于是在 HAL 进程持有了指向 fw 回调的代理）。

2.2 返回值 OpenOutputStreamReturn

写回时的两个关键动作：

  • stream 作为嵌套 binder 序列化：fw 拿到一个新的 BpStreamOut 代理，之后所有流级控制都走它；
  • desc 里的 MQDescriptor<...> 序列化会携带 file descriptor：Binder 驱动把 fd 转发到 fw 进程，双方 mmap 同一块 FMQ 共享内存——这就是 openOutputStream 之后数据面零拷贝的由来。

三、AIDL 的编译配置：Android.bp

写好的 AIDL 会通过 Android.bp 进行编译：

Android.bp 中 aidl_interface { name: "android.hardware.audio.core" } 关键点：

  • stability: "vintf"：稳定 AIDL，必须冻结快照 + VINTF 校验；
  • versions_with_info：V1/V2/V3 已冻结；frozen: false → 当前 V4 还在开发（latest_android_hardware_audio_core = "android.hardware.audio.core-V4"）；
  • backend：cpp: enabled: false（注释写明 “disabled transitively due to use of FMQ”，即 StreamDescriptor 里的 MQDescriptor 只能用 NDK 版 libbinder_ndk 编）；java 开启；ndk/rust 默认开启；
  • aidl_api/android.hardware.audio.core/{1,2,3,current}/ 是冻结 API 快照，编译时 aidl 工具用 --previous_api_dir=…/3 --previous_hash eb5f1f5a… 做兼容性检查（改接口必须同步 update-api）。

四、AIDL 生成物与关键代码分析

AIDL 生成命令会生成对应的 *.h / *.cpp 文件，供 FW 以及 HAL 引用，我的项目上生成的地址在：

  • IModule.cpp：非常重要，负责 Binder 编解码实现（onTransact 分发 + Bp 各方法序列化）；
  • IModule.h：接口类本体（fw/HAL 都 include 它）；
  • BnModule.h：服务端基类 BnModule : ndk::BnCInterface<IModule>，HAL 继承它，含 IModuleDelegator 版本委托；
  • BpModule.h：客户端代理 BpModule : ndk::BpCInterface<IModule>，缓存 version/hash。

七、端到端调用链路（以 openOutputStream 为例）

数据面不走 Binder

  • 控制面：后续走 IStreamOut（AIDL，start/pause/flush/drain 等）；
  • 数据面：走 StreamDescriptor（StreamDescriptor.aidl）：
    • command / reply FMQ：单元素队列，fw 写命令、HAL 写回复（含位置/延迟/xrun）；
    • audio.fmq：音频数据搬运（burst 命令触发）；MMAP No IRQ 模式则用 IStreamCommon.createMmapBuffer 的共享内存（V4 起 audio.mmap 字段废弃）。

fw 侧最终把 IStreamOut/IStreamDescriptor 封装为 StreamOutHalInterface 提供给 AudioFlinger mixer thread——所以你在 dumpsys/atrace 里看到的 binder 事务主要是控制面。

八、小结

  • Android 16 上 Audio FW 与 HAL 之间的交互使用 AIDL + FMQ 替代了 HIDL，但底层仍是 Binder；
  • IModule 是 FW 与 HAL 交互的核心接口，替代 HIDL 的 IDevicesFactory + IDevice；
  • openOutputStream 一次调用同时完成控制面（返回嵌套 binder IStreamOut）与数据面（返回 FMQ 描述符 + fd 传递 → 双方 mmap 共享内存，零拷贝）的建立；
  • 生成代码的 onTransact / Bp 桩是理解“FW 为什么能调到 QTI HAL”的关键，所有 HAL 实现最终都是通过虚函数挂到 BnModule 上的。
