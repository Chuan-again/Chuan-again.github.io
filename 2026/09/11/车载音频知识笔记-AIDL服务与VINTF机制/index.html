速查总览

# 主题 结论
1 QTI AHAL 加载模式 audiohalservice.qti 启动时按板级 vendor_audio_interfaces.xml 逐个 dlopen + dlsym(method) 拉起各 HAL 库，所有 audio HAL 服务都在这一个进程里
2 AutomotiveAudioControl 整个目录经 registerServices() 只注册 1 个服务：android.hardware.automotive.audiocontrol.IAudioControl/default
3 VINTF 声明强制校验 标了 @VintfStability 的接口未在 VINTF manifest 声明 → servicemanager 拒绝注册（EX_ILLEGAL_ARGUMENT "VINTF declaration error."），注意是拒绝而非警告
4 AIDL NDK 后端 生成基于 libbinder_ndk 的绑定（::ndk::BnCInterface、include 带 aidl/ 前缀、模块名 -ndk 后缀），HAL / vendor 服务标准选择
5 binder 线程池 由主程序 main() 统一建池（16 线程）；库代码用 ABinderProcess_isThreadPoolStarted() 检查后复用，不自建
6 部署清单 3 个 .so + VINTF fragment + service_contexts（+ sepolicy / FCM），缺一不可

2.1 结论：只注册 1 个 binder 服务

2.2 注册点：default/Service.cpp

descriptor 字面量（生成代码 IAudioControl.cpp）：
const char* IAudioControl::descriptor = "android.hardware.automotive.audiocontrol.IAudioControl";

2.3 两个易错点

  1. 类名 BnAudioControl ≠ 接口名 IAudioControl
    AIDL 生成 Bn/Bp 类时会去掉接口名的 I 前缀：
    IAudioControl → BnAudioControl.h / BpAudioControl.h + 接口头 IAudioControl.h
    同理 IFocusListener → BnFocusListener.h、IMyService → BnMyService.h
    所以服务名是 .IAudioControl/default，不是 .AudioControl/default

  2. GWMAudioControl 不是第二个服务
    它是 BnGWMAudioControl 子类（IGWMAudioControl 接口的实现），但只通过 setExtension() 挂到 AudioControl 上；
    客户端调的 36 个 gwm_* 方法是直接加在 IAudioControl.aidl 里的，走同一个 binder

2.4 干扰项与死代码识别

对象 真相
NoboAudioControl_AHal.cpp 死代码：未进 Android.mk 源列表、全树 0 引用；内容是反向逻辑（客户端连 android.hardware.audio.core.IModule/default），不是服务端注册
PowerPolicyClient 在 registerAudioControl() 里整段被注释
audiocontrol-default.rc 定义了 init 服务但没有对应二进制被编译，rc 也未进镜像 — 历史遗留
Android.bp_bk 备份文件（文件名不是 Android.bp），不参与构建；其中 init_rc 是注释状态

2.5 分析方法论（查任意目录注册了什么服务）

  1. grep -rn "AServiceManager_addService\|registerAsService\|addService" <目录> 找注册点
  2. 看 Android.mk/Android.bp 源文件列表 → 判断哪些 .cpp 真的被编译（排除死代码）
  3. 追踪导出符号（如 registerServices）被谁 dlsym 调用（查 QTI 的 Service.cpp + 板级 xml）
  4. 用 out/soong（生成物）与 out/target/product（安装物）做最终确认

3.2 校验链路（源码级）

frameworks/native/cmds/servicemanager/ServiceManager.cpp 的 addService() 检查顺序：

meetsDeclarationRequirements（L342-349）：

  • Stability::requiresVintfDeclaration() 实现在 frameworks/native/libs/binder/Stability.cpp L68-70：绑定对象稳定性级别为 VINTF（即接口标了 @VintfStability）时返回 true
  • isVintfDeclared()（L144-199）：把服务名拆成 package / iface / instance（AidlName），遍历 device + framework 两个 manifest 查 hasAidlInstance()
  • 找不到时打印上述日志并 return false → 注册被拒

3.3 manifest 来源与缓存机制

  • Device manifest = /vendor/etc/vintf/manifest.xml + fragments（/vendor/etc/vintf/manifest/*.xml），运行时由 libvintf 合并
  • VintfObject::GetInstance() 是单例缓存：servicemanager 启动后第一次读取就缓存，之后不再重读
  • 改了 fragment 必须重启整机（或 servicemanager）才生效；仅重启音频 HAL 进程无效

3.4 报错日志对照表

日志 含义 对策

Could not find ... in the VINTF manifest fragment 缺失或更新后未重启 补 fragment + 重启
Found <name> in device VINTF manifest. 校验通过（成功标志） —

四、AIDL 后端：NDK vs CPP

4.1 什么是”后端”

AIDL 是接口定义语言；aidl_interface 模块的 backend {} 块决定从同一份 .aidl 生成哪种语言/运行时的绑定代码。共 4 种：ndk、cpp、java、rust。

NDK 后端 = 生成基于 libbinder_ndk 的 C++ 绑定（底层是 ABI 稳定的纯 C 接口 AIBinder_*）。注意这里的 “NDK” 不是指 NDK 工具链，而是指绑定跑在 libbinder_ndk 上。HAL / vendor 服务（MyService、NoboAudioService、audiocontrol）用的全是它。

4.2 Soong 默认行为

system/tools/aidl/build/aidl_interface.go L552-581：四个后端默认全部 enabled=true（注释：故意的，让开发者显式关闭不需要的）。所以：

  • AOSP 的 audiocontrol：-V5-cpp / -V5-java / -V5-ndk 三套都生成
  • 本工程的 MyService：显式 cpp: { enabled: false } → 生成 -V1-java / -V1-ndk / -V1-rust 三套

4.3 对比表

维度 NDK 后端（工程在用） CPP 后端（libbinder 老式）
运行时库 libbinder_ndk（C API + 薄 C++ 封装 ndk::） libbinder（C++，sp<>/IBinder）
命名空间 aidl::vendor::gwm::myservice android::hardware::...（无 aidl::）
服务端基类 BnMyService : ::ndk::BnCInterface<IMyService> BnAudioControl : ::android::BnInterface<IAudioControl>
include 路径 <aidl/vendor/gwm/myservice/BnMyService.h>（带 aidl/） <android/hardware/.../BnFoo.h>（不带）
返回/指针类型 ndk::ScopedAStatus、ndk::SharedRefBase::make<T>()、ndk::SpAIBinder android::binder::Status、sp<>、wp<>
注册 API AServiceManager_addService / _checkService defaultServiceManager()->addService
Soong 模块名 <name>-V1-ndk <name>-V1-cpp
ABI 稳定性 纯 C ABI，跨版本稳定 C++ ABI 不稳定，平台内部使用

4.4 生成物对比（同一接口两套，基类完全不同）

  • CPP 版：out/soong/...-V5-cpp-source/gen/.../BnAudioControl.h
    class BnAudioControl : public ::android::BnInterface<IAudioControl>
  • NDK 版：out/soong/...-V5-ndk-source/gen/include/aidl/.../BnAudioControl.h
    class BnAudioControl : public ::ndk::BnCInterface<IAudioControl>

工程代码 include 的是带 aidl/ 前缀的版本 → 用的 NDK 后端；链接的也是 android.hardware.automotive.audiocontrol-V5-ndk。

4.5 为什么 HAL 服务都选 NDK 后端

  1. ABI 稳定：只暴露 C ABI，system 升级不需要重编 vendor 进程
  2. 版本化治理：-V1-ndk 后缀 + update-api / freeze-api 冻结流程都围绕它设计
  3. VINTF 集成：@VintfStability 标记由 NDK 绑定携带 —— 第三节的强制校验就是针对这类接口
  4. cpp 后端留给平台内部历史代码；java 面向 framework 应用；rust 是新选项

五、binder 线程池：程序建池、库复用

5.1 核心模式

binder 线程池在一个进程内只需要（也建议只）配置一次：由主程序在启动时统一建池，各服务库检查后复用；库代码仅在发现进程内没有池时才兜底自建。这是 libbinder_ndk 头文件中明确的设计约定：

Usually, you should use this in a library to abort if the threadpool is not started.
Programs should configure binder threadpools once at the beginning.

5.2 时序：QTI 主程序先建池

QTI main()（primary-hal/hal/service/Service.cpp）：

调用链：main() → registerAvailableInterfaces() → dlopen → registerServices() → 各服务注册。
因此服务库代码执行到注册逻辑时，进程内已经有 16 个线程的池在运行，服务由主程序的池统一调度。

5.4 API 语义

  • ABinderProcess_isThreadPoolStarted 是 Android 14（U，LIBBINDER_NDK34）起公开的 API
  • 实现（frameworks/native/libs/binder/ndk/process.cpp）：
    return ProcessState::self()->isThreadPoolStarted();
  • 像 audiohalservice.qti 这类主程序已建池的进程，库内兜底分支不会走到，属正常现象
